# 标注指南（S5-6）

> 适用版本：Sprint 5（2026-11-05）
> 配套工具：`scripts/label_report.py`、`scripts/evaluate.py`、`scripts/tune_weights.py`

本指南定义“什么算值得切的高光”、标注文件格式，以及如何把标注用于
Precision@K / Recall@K / Boundary IoU 等指标。目标是让不同人标出的数据
可以直接比较，避免“看起来有指标、实际不可复现”。

---

## 1. 标注集要求

第一版真实基线建议：

| 项目 | 要求 |
|------|------|
| 场次 | 5~10 场 |
| 单场时长 | 30~120 分钟 |
| 类型覆盖 | `default` / `game` / `shopping` / `talent` 至少各 1 场 |
| 每场正样本 | 建议 5~20 个“值得切”窗口 |
| 每场负样本 | 建议 3~10 个“系统容易误判但不应切”的窗口 |
| 边界精度 | 起点/终点误差尽量控制在 ±2 秒内 |

不要只用“系统已经切出来的片段”做标注：那样只能评估 Precision，无法评估
Recall。必须额外浏览完整时间轴，补上系统漏掉的高光。

> 当前仓库还没有真实人工标注集。工具链可用合成数据验证，但对外承诺指标前
> 必须以真实标注跑出基线。

## 2. 正样本与负样本

### 2.1 正样本

同时满足：

- `worthClipping = true`；
- `quality >= 3`（默认阈值，可用 `--min-quality` 调整）。

质量分定义：

| 分数 | 含义 | 例子 |
|------|------|------|
| 5 | 必切，可直接发布 | 完整爆笑桥段、强冲突反转、明确成交话术 |
| 4 | 值得切，稍作修剪 | 有笑点但前后略拖、互动效果不错 |
| 3 | 可切，适合凑量 | 信息完整但不够炸、需要较好标题 |
| 2 | 不建议切 | 平淡聊天、重复动作 |
| 1 | 明确不应切 | 冷场、黑屏、纯背景音乐、无意义等待 |

### 2.2 负样本

`worthClipping = false` 的记录，质量通常填 1。重点标：

- 系统容易误判的弹幕爆发，但实际只是抽奖/机器刷屏；
- 高音量但无内容的喊麦、背景音乐、游戏音效；
- 画面剧烈运动但无信息量的转场；
- 长时间沉默、黑屏、调试画面；
- 重复口播、循环动作。

负样本不是“随便找几个低分片段”，而是**系统真的可能切出来的片段**。否则
`negativeHitRate` 没有诊断价值。

---

## 3. 类型（type）

| type | 用途 |
|------|------|
| `highlight` | 通用高光，无法细分时使用 |
| `funny` | 搞笑、笑点、整活 |
| `high_energy` | 高能、爆发、精彩操作 |
| `interactive` | 弹幕互动、点名、问答、扣 1 |
| `shopping` | 带货讲解、报价、上车、库存 |
| `emotional` | 情感、走心、感谢、故事 |
| `controversy` | 争议、冲突、反转 |
| `dead_air` | 冷场、无内容（通常为负样本） |
| `other` | 其他 |

类型只用于分析，不参与正负判定；正负只看 `worthClipping + quality`。

---

## 4. 边界标注

- 起点：包含触发事件的铺垫，通常比“笑点第一秒”提前 1~3 秒；
- 终点：保留反应/余韵，通常比“笑声结束”延后 1~3 秒；
- 不要为了凑时长硬加无关内容；
- 一个连续事件只标一条，不要切成多条重复记录；
- 两个相邻事件如果中间有明显停顿/话题切换，可以分开标；
- 宁可在 `notes` 里写清楚，也不要留下模糊边界。

Boundary IoU 使用系统片段与标注窗口的时间交集/并集计算，因此边界越准，
IoU 和 Editing Cost 越可信。

## 5. 标注文件格式

对象形式（推荐）：

```json
{
  "roomId": "300294032039",
  "duration": 5400,
  "profile": "game",
  "annotations": [
    {
      "id": "a1",
      "start": 123.5,
      "end": 151.0,
      "type": "funny",
      "quality": 5,
      "worthClipping": true,
      "notes": "连续笑点，前后各留 2 秒"
    },
    {
      "id": "n1",
      "start": 300.0,
      "end": 320.0,
      "type": "dead_air",
      "quality": 1,
      "worthClipping": false,
      "notes": "系统常把这段背景音乐当高能"
    }
  ]
}
```

也支持裸列表：

```json
[
  {"id": "a1", "start": 123.5, "end": 151.0, "quality": 5},
  {"id": "n1", "start": 300.0, "end": 320.0, "worthClipping": false}
]
```

字段说明：

| 字段 | 必填 | 默认 | 说明 |
|------|------|------|------|
| `id` | 否 | `a1`、`a2`… | 文件内唯一；重复会报错 |
| `start` | 是 | — | 秒，支持小数 |
| `end` | 是 | — | 秒，必须大于 `start` |
| `type` | 否 | `highlight` | 见类型表 |
| `quality` | 否 | 正样本 5 / 负样本 1 | 1~5 |
| `worthClipping` | 否 | `true` | 支持 JSON bool 或 `"true"/"false"` |
| `notes` | 否 | 空 | 标注理由，便于复核 |

校验规则：

- `start/end/quality/duration` 必须是有限数字；
- `end > start`；
- `1 <= quality <= 5`；
- `id` 不能重复；
- `annotations` 必须是列表。

## 6. 用 `label_report.py` 降低标注成本

```bash
python scripts/label_report.py \
  --time-table data/300294032039/time_table.json \
  --top 10 \
  --output data/300294032039/label_report
```

脚本会自动选择 `time_table.json` 同目录下最大的 `.mp4`/`.flv` 作为视频源；
需要指定其他文件时加 `--video`。

输出：

```text
data/300294032039/label_report/
├── index.html                    # 自包含审核页，缩略图内嵌
├── annotations.template.json     # 标注模板（可版本控制）
└── media/
    ├── c1.jpg
    ├── c1_context.mp4
    └── ...
```

操作流程：

1. 浏览器打开 `index.html`；
2. 逐个候选选择“值得切 / 不值得切”，填写质量、类型、备注；
3. 在页面底部“新增标注”补上 Top-K 之外的高光或负样本；
4. 点击“导出标注 JSON”，保存到 `data/{roomId}/annotations.json`；
5. 用 `evaluate.py` 计算指标。

说明：

- 未判断的候选不会写入导出文件；导出时会提示还有多少条未判断；
- 缩略图默认取 `thumbnailTime`，上下文视频默认前后各 6 秒；
- 没有 ffmpeg 或视频文件时仍会生成页面，只是没有缩略图/上下文；
- 已有标注可通过 `--annotations` 传入，匹配的候选会自动预填。

常用参数：

| 参数 | 默认 | 说明 |
|------|------|------|
| `--top` | 10 | 展示前 K 个候选 |
| `--context-sec` | 6 | 上下文视频前后留白秒数 |
| `--no-thumbnails` | off | 跳过缩略图 |
| `--no-context` | off | 跳过上下文视频 |
| `--annotations` | — | 已有标注，用于预填 |

## 7. 评估指标口径

系统片段与人工标注采用**一对一最大基数匹配**：一个系统片段不能同时命中
两个标注，避免重复片段刷高 Recall。

| 指标 | 口径 |
|------|------|
| Precision@K | 前 K 个系统片段中，匹配到正样本的比例；分母为 `min(K, 实际片段数)` |
| Precision@K (strict) | 分母固定为 K，便于不同场次横向比较 |
| Recall@K | 前 K 个片段命中的正样本数 / 全部正样本数 |
| Boundary IoU | 匹配片段的平均时间 IoU |
| Invalid Rate | 前 K 个片段中未匹配到正样本的比例 |
| Duplicate Rate | 前 K 个片段中与更高排名片段 IoU ≥ 0.5 的比例 |
| Editing Cost | 匹配片段的平均边界调整秒数：`|start 差| + |end 差|` |
| Negative Hit Rate | 被系统片段命中的负样本比例 |

初始目标（**建议值，不是硬承诺**）：

| 指标 | 初始目标 |
|------|----------|
| Precision@K | ≥ 0.60 |
| Recall@K | ≥ 0.70 |
| Boundary IoU | ≥ 0.50 |
| Invalid Rate | ≤ 0.20 |
| Duplicate Rate | ≤ 0.10 |

第一次真实标注跑完后，应把实测基线写入项目记录，再决定是否调整目标。

## 8. 常见问题

**Q: 一个高光被系统切成两段，怎么标？**
A: 人工只标一条完整窗口；评估时一对一匹配只会算一次，另一段会计入
Invalid/Duplicate。不要为了迁就系统而拆成两条。

**Q: 这段“有点意思但不会发”，算正样本吗？**
A: 质量填 2，`worthClipping=false`。正样本门槛是“值得切”，不是“不讨厌”。

**Q: 弹幕很多但内容无聊，算高光吗？**
A: 不算。弹幕爆发只是系统信号，不是人工认可理由；这类正是重要负样本。

**Q: 标注必须覆盖全片吗？**
A: 评估 Recall 需要覆盖全片。至少完整浏览一遍，重点补系统未切出的高光。

**Q: 可以多人标注同一场吗？**
A: 可以，但需要先合并成一份 `annotations.json`；重复 `id` 会报错。建议一人
主标、一人抽检，不要直接把两份文件堆在一起。
